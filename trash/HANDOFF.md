## 1. Project Overview — OrcFuzz

OrcFuzz is a coverage-guided fuzzer for **crun** (an OCI container runtime, the `vendor/crun` C codebase). It fuzzes two surfaces simultaneously:

- **OCI config JSON** — generated by a **Nautilus context-free grammar** (`grammar.py`) as derivation trees (`NautilusInput`).
- **Container rootfs** — a **FUSE-backed in-memory virtual filesystem (VFS)**. All rootfs reads/writes are served from memory; **zero host disk I/O**. The rootfs is mutated via an `FsDelta` (a list of `FsOp` operations: create file, mkdir, write, rename, symlink, unlink, etc.).

The combined input type is:

```rust
pub struct CombinedInput {
    pub config: NautilusInput,   // OCI config grammar tree
    pub rootfs: FsDelta,         // rootfs mutation operations
}
```

### Fuzzing engine
- Built on **LibAFL** pinned at commit `277d15d` (`277d15d751184301d4e7b6a106bb3d6930f5b431`), checked out at `/home/arjun/.cargo/git/checkouts/libafl-df9415290f13ce43/277d15d/`.
- Uses LibAFL's **`ForkserverExecutor`** driving an **AFL++ LTO-instrumented** crun binary (the target is compiled with AFL++ instrumentation, NOT LibAFL's own instrumentation).
- Coverage map is **AFL++ System V SHM** (65536 bytes, `__AFL_SHM_ID`), wrapped in `HitcountsMapObserver` + `StdMapObserver` + `MaxMapFeedback`.

### Main fuzzer binary
`mutator/src/bin/fuzz_combined_afl.rs` → builds to `mutator/target/release/fuzz_combined_afl`.

## 2. LibAFL API facts (commit 277d15d) — these bit us repeatedly

These exact signatures were discovered by reading the checked-out LibAFL source. Use them; don't guess:

- `Feedback<EM, I, OT, S>` — **4 type params** (not 1).
- `Observer<I, S>` — 2 params.
- `EventFirer<I, S>` — **2 params** (`crates/libafl/src/events/mod.rs:415`).
- `StateInitializer<S>` — separate trait from `Feedback`.
- `State` is a **private** trait — you cannot name `S::Input`; use the `I` generic instead.
- There is **no `discard_metadata`** method on `Feedback`.
- `Evaluator::evaluate_input(&mut state, &mut executor, &mut mgr, &input)` — takes `&input` (reference). Returns `Result<(ExecuteInputResult, Option<CorpusId>), Error>`.
- `ExecuteInputResult` enum: `None | Corpus | Solution` (in `crates/libafl/src/fuzzer/mod.rs:278`).

## 4. Shared Corpus Across 6 Instances (IMPLEMENTED — coverage-gated version is current)

### Design rationale (final decision, do not re-litigate)
**Per-instance corpus dirs + a shared sync dir** — NOT a single shared corpus dir.
- Why not single shared dir: LibAFL `OnDiskCorpus.add()` re-writes imported entries under a new local `CorpusId`, so other instances would re-import → re-export → N² duplication spiral. Also `OnDiskCorpus` writes raw `postcard` binary, which we'd have to round-trip through LibAFL's loader, re-triggering export.
- The sync dir is a **one-way publish channel**: each instance publishes its OWN discoveries once; peers consume once. `seen_foreign` (a `HashSet<String>` of filenames) prevents re-import and self-import.

### How it works in `fuzz_combined_afl.rs`
**CLI args added:**
- `--sync-dir <path>` — shared dir (`/tmp/c3_shared`).
- `--instance <N>` — instance id 0..5, used to name exports.
- (existing `--resume` still works.)

**Export (push):** in the `before..after` loop after each `fuzz_one`, every newly-added local corpus entry is serialized as JSON (`serde_json::to_vec(&CombinedInput)`) to `{sync_dir}/i{N}_{idx}.sync`, and its filename inserted into `seen_foreign` (so we never re-import our own).

**Import (pull):** every **256 fuzz iterations** (`sync_tick % 256 == 0`), scan the sync dir for `.sync` files not in `seen_foreign`, sorted, **capped at 32 per tick** (so a backlog can't stall the loop). For each:
1. Insert filename into `seen_foreign`.
2. Deserialize to `CombinedInput`.
3. **`fuzzer.evaluate_input(&mut state, &mut executor, &mut mgr, &input)`** — this is the AFL++-style coverage gate. It actually RUNS the input against crun, collects the AFL++ bitmap, and runs feedbacks. Only `ExecuteInputResult::Corpus` (hit a new edge / new FS path in THIS instance's virgin map) gets kept + sidecar-written + pushed to `live_corpus` + added to `NautilusChunksMetadata`.

### The bloat history
- **v1 (blind):** import = `state.corpus_mut().add(Testcase::new(input))` with no check. User observed early corpus explosion (19,086+ entries quickly). This was changed on June 6th.
- **v2 (current code, coverage-gated):** uses `fuzzer.evaluate_input()`. Running for ~40 hours. Corpus is still ~156k entries per instance, sync dir ~457k files. **The gate reduced bloat compared to blind import but did not fully control it.** The remaining bloat is driven by `FsAccessFeedback` (new FS path = interesting) and `TimeFeedback` (new slowest execution = interesting) wired into the same `feedback_or!` that evaluate_input uses. AFL++ queue sync only admits on new edges — our gate is broader.

### Honest differences from real AFL++ sync (told to user)
The coverage check is equivalent, BUT:
1. We use `feedback_or!(MaxMapFeedback, TimeFeedback, FsAccessFeedback)` — so `TimeFeedback` (slowest-exec) or `FsAccessFeedback` (new FS path) can also admit an import, not just new edges. AFL++ checks coverage only. Slightly more permissive.
2. We cap 32 imports/tick; AFL++ drains the full backlog per sync.
3. Sync cadence is every 256 iterations (~5s at 50 exec/s) vs AFL++'s time-based dynamic interval.
None of these reintroduce unbounded bloat; all are minor and in the "slightly permissive" direction.

### Why not use LibAFL LLMP (the "proper" multi-instance mechanism)?
LLMP (Low-Level Message Passing) is LibAFL's real broker-based multi-instance solution (broker + shared-mem ring, clients re-check coverage locally). We did NOT use it because it requires replacing `SimpleEventManager` with `LlmpRestartingEventManager` + broker bootstrap + serializing `CombinedInput` over shared mem + reconciling the forkserver-death restart logic + each client owning its own `Box::leak`'d `NautilusContext`. ~1 day of work and easy to get subtly wrong (silent hangs). The file-based sync is a pragmatic, correct approximation. **Upgrading to LLMP is a candidate future task if multi-instance becomes central.**

## 6. Coverage Context (for interpreting results)

- Latest measured LLVM coverage: ~22.66%. AFL++ virgin-map coverage shows a similar number.
- **Theoretical ceiling ~30–35%.** ~15% of crun is structurally unreachable from this harness: `cgroup-systemd.c`, `criu.c`, most CLI subcommands, `net_device.c`.
- **Fork/exec blindspot (measurement only, NOT a fuzzing-effectiveness problem):** LLVM's `atexit` coverage flush is cleared when the child calls `execve()`, so LLVM-replay misses child-side code. AFL++ SHM is System V IPC that survives both `fork()` AND `exec()`, so AFL++ genuinely captures child-side coverage. This is why AFL virgin-map ≈ LLVM number despite the theoretical concern — the campaign IS covering that code; only the LLVM *replay measurement* would under-count.
- Low-coverage file of interest: `cgroup-setup.c` (8.36%). Grammar Patch 3 (cgroup cpuset/memory resources) is a deprioritized option to push it.
- Harness clamps memory limit to ≥128 MiB (grammar can emit tiny limits like `1` byte that OOM-kill crun itself and crash the forkserver — clamping preserves cgroup-path coverage without spurious deaths).

## 7. NEXT TASK (in progress, NOT yet built): Replay recorded crashes with ASAN

The user's immediate goal: **triage recorded crashes to separate genuine bugs from spurious crashes** by replaying each through the ASAN crun binary. This is correct methodology:
- ASAN reports a memory error → **genuine bug**.
- ASAN exits clean / non-memory error (e.g. OOM kill from tiny resource limit, invalid-config abort) → **spurious**.

### What needs building (a replay script). Key facts to design it:
- Crashes are stored per-instance in `/tmp/c3_<i>/crashes/` as a LibAFL `OnDiskCorpus`: each entry is `combined_<N>` (raw postcard binary) PLUS a sidecar `combined_<N>.json`.
- **Sidecar JSON format** (from `write_corpus_sidecar`):
  ```json
  { "config": "<full OCI config JSON as a string>", "ops": [ <FsOp array = the rootfs FsDelta> ] }
  ```
- **Replay complication — the rootfs is FUSE-backed.** The `config` string's `root.path` points at the campaign's FUSE mountpoint (`/tmp/campaign3-fuse-<pid>`), which won't exist at replay time. So to faithfully replay you must EITHER:
  1. Reconstruct a real rootfs dir by applying the `ops` (the `FsDelta`) to a temp directory and rewrite `root.path` to it, OR
  2. Stand up the same FUSE VFS, apply the delta, mount it, and point `root.path` there (mirrors campaign exactly).
  Option 1 is simpler for one-off triage; option 2 is faithful. Discuss with user which they want.
- The ASAN binary to use: `/nix/store/4w5j3vmpd4rl71c0vxzkl5mwq4mqjnz7-crun-harness-asan-1.23.1/bin/crun` ("with ASAN & No False Positives").
- Run crun the same way the harness does: `crun <config.json>` (config path is argv[1]; the harness loop reads argv[1], creates `rootfs/` subdirs `tmp proc sys dev dev/shm`, then `libcrun_container_run`). Replay likely needs to run under `sudo unshare -m` like the campaign.
- ASAN output → `/tmp/asan_reports/crun_asan.<pid>` (created automatically by the harness constructor).

### Suggested script behavior (confirm with user before building)
